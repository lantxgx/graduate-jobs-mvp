# 牛投马面长期开发基线

版本：WB-BL-1.0  
维护者：Codex  
适用对象：WorkBuddy/HY3 以及后续本地执行模型

本文件是所有 WorkBuddy 任务的长期基线。单次任务只能在明确写出“覆盖哪条基线、为什么、如何迁移和如何回滚”时改变本文件中的规则。任务没有写覆盖说明时，以下规则全部生效。

## 1. 产品目标基线

“牛投马面”是面向应届生的企业官方招聘岗位聚合与辅助决策产品，不是普通招聘站的镜像，也不是只输出 AI 推荐结果的黑盒。

产品必须同时保留两条入口：

1. **完整检索入口**：用户不填写简历也能搜索全部有效岗位；
2. **画像推荐入口**：用户确认能力证据和求职意愿后，AI/规则只负责召回、排序、解释和扩展相邻岗位。

推荐不能删除完整检索中的岗位。AI 可能漏召回，因此“全部岗位”永远是产品基线。

## 2. 当前权威状态

执行任何任务前必须通过数据库和接口重新核对，不能只相信文档数字。当前参考值：

- 活动岗位约 631 条；
- 已接入企业 6 家：小米、小鹏、叠纸、OPPO、米哈游、MiniMax；
- 企业注册表约 52 家、招聘入口约 64 个；
- 活动岗位招聘类型只能是 `全职`、`实习`；
- 隔离和失败证据必须保留；
- 数据库：`data/jobs.db`；
- 本地服务：`http://127.0.0.1:8000/`；
- 全量测试基线：至少 91 项通过。测试数量增加可以，减少必须解释并由 Codex 审核。

权威性顺序：

```text
当前数据库/接口/真实文件
> 当前任务中的明确事实
> 本基线
> README 和历史方案文档
> 模型记忆或猜测
```

## 3. 页面与职责边界

### 3.1 找岗位 `/`

只承担用户岗位发现与决策：

- 搜索岗位、技能和关键词；
- 按公司、城市、职能、岗位族、全职/实习、学历筛选；
- 显示公司、城市、职能、岗位、招聘类型、学历、描述、要求、官方投递链接；
- 查看全部、收藏、不感兴趣、已投递；
- 在用户主动点击后显示画像推荐；
- 企业目录只显示已经有活动岗位的企业。

不得把待验证企业、入口探查日志、采集按钮、数据库质量 JSON 塞进找岗位页面。

### 3.2 我的画像 `/profile`

只承担用户能力证据和求职意愿确认：

- 简历上传是可选项；
- 简历解析只生成候选能力证据；
- 求职意愿必须由用户确认，不能从简历强行推断；
- 用户可以填写主攻岗位、相邻岗位、目标企业、目标城市、明确排除岗位；
- 推荐比例合计必须为 100%；
- 原始简历不长期保存，只保存用户同意的结构化画像。

### 3.3 数据管理 `/admin/sources`

只承担运营与采集控制：

- 企业和招聘入口状态；
- 官方归属、ATS、访问状态、接入状态、质量和优先级；
- 待接入队列、采集运行、快照保护、岗位隔离；
- 页面加载和普通筛选不得触发真实采集。

## 4. 岗位数据基线

活动岗位必须满足：

| 产品字段 | 数据字段 | 规则 |
|---|---|---|
| 公司 | `company` / `company_id` | 标准企业名称，不使用重复别名 |
| 城市 | `city` | 明确地点；多城市使用 ` / ` |
| 职能 | `category` | 受控中文分类 |
| 岗位 | `title` | 具体岗位，不是招聘计划、项目、宣讲会或入口导航 |
| 招聘类型 | `job_nature` | 只能是 `全职` 或 `实习` |
| 学历 | `degree` | 未注明、大专及以上、本科及以上、硕士及以上、博士 |
| 描述 | `description` | 企业公开原文或确定性清洗结果 |
| 要求 | `requirements` | 企业公开原文或确定性清洗结果 |
| 官方投递 | `apply_url` | 具体岗位详情或投递 URL，禁止猜测 |
| 来源 | `source_url` | 官方招聘入口 |
| 来源岗位ID | `source_job_id` | 来源有稳定 ID 时必须保存 |

`description` 和 `requirements` 至少一个非空。活动岗位必填字段缺失数必须为 0。

禁止进入活动岗位：

- 企业招聘首页；
- 校招计划或活动介绍；
- 宣讲会；
- 导航卡片；
- 没有具体详情/投递链接的列表对象；
- 无法判断全职/实习的记录；
- 明确社招、兼职、劳务或外包岗位；
- 模型推测出来的城市、学历、职责、要求或 URL。

## 5. 招聘类型基线

唯一合法值：

```text
全职
实习
```

映射规则：

- 实习、实习生、intern、internship → `实习`；
- 正式、校招、应届、graduate、new grad、full-time → `全职`；
- 社招、兼职、外包、劳务或无法判断 → 拒绝/隔离；
- 同时出现“校招”和“实习”时 → `实习`；
- 禁止把空值默认成全职。

## 6. 职能基线

`category` 只能使用：

```text
算法/AI、软件研发、硬件研发、测试/质量、数据、产品、运营、设计、
市场/销售、制造/工艺、供应链/采购、职能、其他
```

分类优先级：明确岗位标题/来源分类 > 确定性关键词 > AI 候选建议。AI 建议不能覆盖原始证据。招聘、人才、HRBP、Talent Partner 等明确人力岗位属于 `职能`，不能因为描述中出现 AI 就归为算法。

## 7. 采集边界

每个真实来源必须按 S1-S8 执行：

```text
S1 官方入口确认
S2 脱敏本地 fixture
S3 适配器实现
S4 离线标准化测试
S5 最多 20 条真实受控样本
S6 入库与前端验证
S7 调度资格确认
S8 Harness 记录
```

访问顺序：公开 JSON/API → 服务端 HTML → 必需时 Playwright。禁止代理池、指纹伪装、验证码绕过、登录墙绕过、租户/岗位 ID 枚举和猜测详情 URL。

遇到 403、429、验证码、安全验证、登录墙立即暂停，不自动重试。WorkBuddy 默认无权执行 S1、S5、S7；除非任务明确授权并提供对应 Skill/连接器。

## 8. 自动更新基线

- 单来源串行；
- 每轮调度最多处理一个到期来源；
- 默认来源更新间隔约 12 小时；
- 列表未变化时不重复请求全部详情；
- 新增、变化或详情过期时才取详情；
- 一次岗位消失不能立即下线；
- 连续 3 次健康完整快照缺失后才允许转 inactive；
- 空快照或岗位数下降超过 50% 必须保护现有岗位；
- 详情失败不能覆盖已有有效详情；
- Web 服务启动不得自动触发采集。

## 9. 推荐系统基线

推荐至少保留四类岗位池：

- 主攻方向；
- 用户点名的目标企业；
- 相邻方向；
- 少量探索岗位。

销售类岗位不能因为关键词重合而大量进入算法/研发用户的推荐。用户明确排除销售时，推荐默认排除，但完整检索仍可查。算法岗位竞争高时，可推荐技能相邻的数据、工程、测试开发等岗位，并说明转型距离和证据，不能假装完全匹配。

## 10. 文件与修改边界

- 单任务只修改 `TASK.md` 允许的文件；
- 现有用户改动默认保留；
- 不进行无关重构、重命名、格式化全仓库或依赖升级；
- 不修改 `.env`；
- 不把密钥写入代码、日志、测试、任务或 Harness；
- 不删除历史岗位、来源、失败记录、隔离记录和快照证据；
- 不执行 `git reset --hard`、`git checkout --` 或递归删除；
- 临时调试代码必须在交付前移除；
- 不为了测试通过降低质量门禁或删除断言。

## 11. Python 书写规范

- 使用现有模块边界，不为单一来源重写框架；
- 适配器只返回标准对象，不直接写数据库；
- 数据写入通过现有 runner/upsert；
- 所有外部数据使用 `.get()`、类型判断和空值处理；
- 函数保持单一职责，复杂逻辑增加简短 docstring；
- 不使用裸 `except:`；
- 错误原因使用稳定、可检索的英文代码；用户界面再映射中文；
- 测试使用本地 fixture，不在单元测试中访问网络；
- 新规则至少提供一个正例和一个拒绝/边界例。

## 12. JavaScript/HTML/CSS 书写规范

- 使用原生 JavaScript，不引入新框架或依赖；
- DOM 查询集中、命名表达业务含义；
- 查询参数用 `URLSearchParams`；
- 用户输入放入 `textContent` 或表单值，禁止拼接到 `innerHTML`；
- 异步请求处理失败状态，向用户展示中文错误；
- 不增加自动采集、无限轮询或隐藏网络请求；
- 保持键盘可操作、label 与表单关联、按钮声明 `type="button"`；
- 中文文案面向普通用户，内部枚举使用映射显示；
- 保持移动端已有断点，不让表格或按钮溢出；
- 修改 JS/CSS 后更新静态资源版本参数，避免旧缓存。

## 13. 测试和交付基线

最低验证：

```powershell
& .\.venv\Scripts\python.exe -m compileall -q app crawler tests
& .\.venv\Scripts\python.exe -m unittest discover -s tests -p 'test_*.py' -q
node --check static/app.js
node --check static/admin-sources.js
Invoke-WebRequest -UseBasicParsing http://127.0.0.1:8000/health
```

任务必须写出实际命令、退出码、测试数量。不得只写“应该通过”或“测试通过”。不能运行的验证要写清原因和替代证据。

## 14. 回溯基线

每个任务必须拥有唯一 `task_id`。回执必须记录：

- 任务开始/结束时间；
- 执行模型；
- 修改文件；
- 修改前基线；
- 逐项改动；
- 验证命令和完整结果摘要；
- 外部访问、数据库修改和密钥接触情况；
- 遗留风险；
- Codex 验收结论。

WorkBuddy 不得自行将任务标记 `accepted`。只有 Codex 核对真实文件、测试和运行行为后才能接受。
